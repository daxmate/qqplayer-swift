## 0. 怎么用这份文件

1. 每个实体六列：**用户可见承诺 / 权威端与冲突 / 删除 / 触发 / 失败披露 / 身份键**。缺一列不算定义。
2. **「不承诺」也是承诺**：本文件写明"不做"的，任何人不得实现它——防止再出现"承诺了做不到"或"没承诺却偷偷做"。
3. 修改流程：**改本文件 → 用户确认 → 才动代码**。禁止用追加章节"覆盖"前面的定义（历史教训：§12b 覆盖 §6）。
4. 验收从本文件生成，不从"发现的 bug"生成。

## 3. 全实体通用规则

1. **删除一律不传播**（用户 2026-09-10：「删除是自己的事情」）。
2. **触发**：连接就绪后自动跑一轮（补发不依赖用户动作）+ 面板手动可再跑。
3. **失败必须分类计数并上屏**，禁止静默；「已应用 N」必须等于**真落库行数**（丢弃、跳过、歧义不算应用）。
4. **身份**：跨端恒用 `content_hash`；端内 `stableId` 只在本端使用，**永不上线**。
   - `content_hash` 缺失时，以**曲库相对路径为第二身份**（唯一命中才落库；歧义不落库并计数；
     本地无此歌则按相对路径挂起）。相对路径是两端统一的跨端键（Mac 推送文件时就是按相对路径
     落到 iOS 曲库）。解析顺序 = `content_hash` 优先，**存在指纹时绝不看相对路径**。
   - 边界：**曲库根之外**的文件（例如 macOS 设置页添加的外部音乐文件夹）算不出相对路径 = 没有
     第二身份，行为与今天相同（该行不改判为错误，只是仍按「未定位」计数）。
   - 两把键都拿不到 = 真空缺 → 不落库、不挂起，**计数上屏**。
5. **业务数据只走数据通道**；内容通道只搬字节，不改业务状态。
6. **移动端纯被动**（不主动同步、不主动上传）；发起方为桌面端。
